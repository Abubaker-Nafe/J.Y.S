`# JYS Feature Opportunity Review

**Review date:** 2026-08-03  
**Scope:** Analysis and proposals only. No recommendation in this report has been implemented.

## Executive summary

JYS is already a mature, coherent first-release e-commerce application rather than a prototype. It has a bilingual Arabic/English storefront, resilient account/session states, a real PostgreSQL commerce model, server-authoritative pricing and stock, cash delivery/pickup checkout, persistent customer cart and wishlist, order history, and an unusually broad admin workspace. Its automated coverage is also stronger than most projects at this stage: the repository records 132 unit/component/service tests plus database, storefront, hostname, responsive Chromium, and responsive WebKit journeys.

The current local database contains 31 product records, of which 6 are active, 77 orders, 79 carts, 39 wishlist rows, 61 product views, and 43 customer addresses. These counts are **not business analytics**: the database includes deterministic seed data and records generated by prior E2E runs (including a disproportionate number of cancelled test orders). They are useful only as an architectural and current-catalog scale signal. No conversion, demand, or profit claim below is presented as proven customer behavior.

- **Biggest customer opportunity:** connect saved addresses to checkout. A registered customer can maintain default addresses, but checkout currently uses only the session name and asks for phone, city, area, street, and location details again.
- **Biggest admin opportunity:** turn existing dashboard/report signals into direct work queues, and add safe product duplication for the long bilingual product/variant form.
- **Biggest profitability opportunity:** make repeat buying easy now, then use clean post-launch order data to improve complementary-product recommendations. The likely mechanisms are repeat-order conversion and higher average order value; both require measurement.
- **Biggest operational risk:** customer-visible order tracking currently exposes notes that the admin UI calls internal, while outbound order email has no durable delivery/retry path. Separately, production backups, durable image storage, and a real email provider remain manual launch gates already documented in `SETUP_CHECKLIST.md`.
- **Recommended first improvement phase:** fix the four bugs below first, then implement REC-001 through REC-005. Add baseline funnel measurements before evaluating the later conversion and retention ideas.

### Evidence and exploration boundary

The review covered the requested documentation, package scripts and environment inventory, Prisma schema and four migrations, seed policy/data, storefront/admin/API route inventories, domain services, reports/CSV, navigation, responsive CSS, and current Git diff. The development server was started and read-only requests verified healthy English and Arabic public, auth, account-shell, checkout, and admin-shell routes. PostgreSQL was queried read-only for the non-sensitive counts above; no row was changed.

The session's interactive in-app browser backend reported that no browser was available, so fresh manual clicks, console inspection, and screenshots could not be performed. This limitation was not bypassed with a different automation system. Journey evidence therefore combines live same-origin HTTP responses, source inspection, and the repository's immediately current Playwright evidence. That evidence covers visitor storefront behavior, real customer/admin PostgreSQL flows, localhost/custom-host auth, 26 raw portrait/landscape sizes, iPhone SE/13/15 Pro Max, Galaxy S9+/S24, Pixel 5, and Chromium/WebKit tablets. Firefox is opt-in and is documented as unable to create a page on this Windows runner. Physical iPhone/Android testing remains a manual release step; this report does not claim otherwise.

### Scoring convention

All scores use 1 to 5. For **customer value, admin value, revenue potential, and operational value**, 5 is strongest. For **implementation effort, maintenance cost, technical risk, and business-decision dependency**, 5 is most costly, difficult, or dependent. Expected benefits are informed estimates unless explicitly measurable from current behavior.

- Server-authoritative sale pricing and checkout validation, stale-price acknowledgement, stock limits, transactional order creation, cash-only delivery/pickup rules, and immutable order snapshots.
- Required customer accounts, persisted database cart/wishlist, profile management, saved/default addresses, order ownership protection, status history, print support, and finite loading/error/retry states.
- Role-aware storefront entry into the admin area and server-enforced denial/redirect for customer accounts.
- Admin product, image, variation, sale scheduling, category, inventory, order, customer, location, content, settings, reports, print, and five CSV export workflows.
- Inventory deduction/restoration idempotency, concurrency control, explicit adjustment reasons, low/out-of-stock filters, and a ledger.
- Report filters for date, order/payment/fulfilment/category; revenue, AOV, customer, product, category, view, wishlist, active-cart, stock, and delivered-order pair signals.
- Security controls including server authorization/ownership, request parsing and size limits, same-origin mutation validation, production cookie/header policy, password hashing, bounded rate limiting, safe uploads, audit records, and CSV formula neutralization.
- Replaceable email and image-storage interfaces, health endpoint, migration/seed safety documentation, and clear production configuration handover.

## Recommendations

## Tier 1 — Highest-value, low-to-moderate effort

### REC-001 — Use saved addresses and stored contact data at checkout

- **Category:** Customer convenience; conversion; mobile forms.
- **Priority:** High.
- **Time horizon:** Implement now, after BUG-001 through BUG-003 are contained.
- **Size:** Medium.
- **Current behavior:** Account address management supports multiple addresses and a default address. Checkout pre-fills only `user.name`; phone and all delivery fields are blank, and the first city is selected independently of the customer's default address.
- **Observed limitation or opportunity:** The account requirement should reduce repeat data entry, but the most valuable saved account data is disconnected from the ordering journey. This is especially costly on a phone and for long Arabic addresses.
- **Proposed feature or change:** Load active saved addresses after session resolution, select the default automatically, show compact address cards/radios, and retain a clear **Use a different address** option. Prefer an optional `addressId` submitted to checkout and resolve/validate current ownership server-side; copy the resulting fields into the existing immutable order snapshot. Pre-fill stored phone for pickup too. Let the user explicitly choose whether a new address should be saved.
- **Customer benefit:** Faster, less error-prone repeat checkout with fewer keyboard interactions.
- **Admin benefit:** Cleaner phone/address data and fewer clarification calls.
- **Revenue or profitability mechanism:** Potentially reduces checkout friction and address-related abandonment; the benefit requires funnel measurement.
- **Evidence from the current website:** `CustomerProfile.defaultAddressId`, `Address`, `/api/account/addresses`, and `address-manager.tsx` already exist, while `checkout-client.tsx` uses only `user?.name` and builds delivery fields from blank inputs.
- **Main routes/files/modules affected:** `/{locale}/checkout`, `checkout-client.tsx`, `/api/checkout`, `/api/account/addresses`, `src/lib/validation/commerce.ts`, `src/lib/domain/order-service.ts`.
- **Database changes:** None required for selection. The existing order snapshot remains authoritative. Optional analytics events would be a separate REC-007 decision.
- **External service or recurring cost:** None.
- **Security/privacy considerations:** The server must resolve `addressId` under the authenticated user, reject inactive/stale addresses, and never trust address fields from another account. Avoid exposing full addresses in logs.
- **Arabic/English considerations:** Localize selection/change/save labels; keep phone LTR within RTL; test long labels, city/area names, and address wrapping.
- **Phone/tablet considerations:** Use stacked cards and 44 px controls; do not render a dense desktop select; keep manual-entry fields scrollable above the keyboard.
- **Risks:** A default address can be stale or a city can be disabled after it was saved. Show a specific correction path rather than silently submitting it.
- **How success should be measured:** Saved-address selection rate, checkout field-validation rate, median checkout completion time, checkout-start-to-order conversion, and address-related support corrections.
- **Scope classification:** Fits current scope.
- **Scores:** Customer value 5; Admin value 3; Revenue potential 4; Operational value 4; Implementation effort 3; Maintenance cost 2; Technical risk 2; Business-decision dependency 1.

### REC-002 — Add a stock- and price-safe “Buy again” workflow

- **Category:** Customer retention; customer convenience.
- **Priority:** High.
- **Time horizon:** Implement now.
- **Size:** Medium.
- **Current behavior:** Order history provides status, total, date, and a details link. Order detail shows item links and historical snapshots but offers no reorder action.
- **Observed limitation or opportunity:** Barber supplies are naturally replenishable. A returning customer must rediscover each prior item and variation individually.
- **Proposed feature or change:** Add **Buy again** on eligible order cards/details. Resolve every current product and `variantId`, current price, active state, and current stock before writing to the active cart. Present a review result showing added items, adjusted quantities, changed prices, and unavailable/archived items. Never copy historical price snapshots into the cart and never skip warnings silently.
- **Customer benefit:** Converts a multi-step repeat purchase into one reviewed cart action.
- **Admin benefit:** Fewer product-identification questions and less manual order recreation.
- **Revenue or profitability mechanism:** Likely encourages repeat purchases and shortens time to reorder; actual effect depends on reorder frequency.
- **Evidence from the current website:** `OrderItem` already retains nullable `productId` and `variantId`; `getCustomerOrder` already enforces ownership; cart services already validate current price/stock. `order-history.tsx` and `order-detail.tsx` expose only view/print actions.
- **Main routes/files/modules affected:** `/{locale}/profile/orders`, `/{locale}/profile/orders/[id]`, `/api/account/orders/[id]`, `/api/cart`, `order-detail.tsx`, `order-history.tsx`, cart/catalog domain services.
- **Database changes:** None required.
- **External service or recurring cost:** None.
- **Security/privacy considerations:** Reorder must be owner-only, bounded by item/quantity limits, same-origin protected, and reuse the existing server-authoritative cart rules.
- **Arabic/English considerations:** Translate partial-success explanations naturally and preserve historic bilingual labels when a product no longer exists.
- **Phone/tablet considerations:** Use one clear full-width action and an accessible review summary; avoid a modal wider than the viewport.
- **Risks:** Customers may assume historical pricing or exact availability. The review step and explicit changed/unavailable messages are essential.
- **How success should be measured:** Buy-again usage, percentage reaching cart, reordered-cart checkout conversion, repeat-purchase interval, and item exception rate.
- **Scope classification:** Fits current scope.
- **Scores:** Customer value 5; Admin value 2; Revenue potential 4; Operational value 2; Implementation effort 3; Maintenance cost 2; Technical risk 3; Business-decision dependency 1.

### REC-003 — Add a mobile purchase bar when the main product action is off-screen

- **Category:** Mobile usability; conversion.
- **Priority:** High.
- **Time horizon:** Implement now, then measure through REC-007.
- **Size:** Small.
- **Current behavior:** On narrow screens the full image/gallery, title, price, description, and variations precede the main quantity/Add to cart row. There is no persistent purchase access once that row scrolls away.
- **Observed limitation or opportunity:** The existing responsive layout is contained and usable, but buying requires returning to one position in a long product page. This is an informed mobile-conversion opportunity, not a reproduced overflow bug.
- **Proposed feature or change:** Show a compact safe-area-aware bottom bar only while the primary Add to cart row is outside the viewport. Display current effective price and an Add to cart/focus-variation action, share the same selected variation and stock state, and never duplicate announcements. Use `IntersectionObserver`, normal document flow fallback, and `prefers-reduced-motion`.
- **Customer benefit:** Keeps the primary purchase action reachable without covering product information.
- **Admin benefit:** None direct.
- **Revenue or profitability mechanism:** May improve product-to-cart conversion on phones; validate rather than assume.
- **Evidence from the current website:** DOM order in `product-detail-client.tsx`; the project already has safe-area utilities and mobile viewport tests, but no sticky purchase component.
- **Main routes/files/modules affected:** `/{locale}/product/[productId]`, `product-detail-client.tsx`, shared button/safe-area CSS, responsive Playwright assertions.
- **Database changes:** None.
- **External service or recurring cost:** None.
- **Security/privacy considerations:** None beyond existing cart mutation controls.
- **Arabic/English considerations:** Price/order should mirror correctly, variation warnings must fit Arabic, and the control needs one unambiguous accessible name.
- **Phone/tablet considerations:** Apply only where useful; include bottom safe-area inset, keyboard/menu/dialog coexistence, landscape, 320 px width, and zoomed-text tests.
- **Risks:** A persistent bar can cover content or create duplicate focus targets. Hide it when the original action is visible and reserve enough bottom space only while active.
- **How success should be measured:** Product-view-to-cart rate by viewport, action usage, variation-error rate, accidental removal rate, and accessibility/geometry regression tests.
- **Scope classification:** Fits current scope.
- **Scores:** Customer value 4; Admin value 1; Revenue potential 4; Operational value 1; Implementation effort 2; Maintenance cost 2; Technical risk 2; Business-decision dependency 1.

### REC-004 — Duplicate a product safely as a draft

- **Category:** Admin productivity; catalog operations.
- **Priority:** High.
- **Time horizon:** Implement now.
- **Size:** Medium.
- **Current behavior:** Creating a related product repeats bilingual names/descriptions, category, threshold, variation labels, pricing structure, images, and availability settings through one long form. Product list actions are Edit, Inventory, and Archive/Restore only.
- **Observed limitation or opportunity:** Similar barber products and size/model variants create avoidable repeated data entry and translation risk.
- **Proposed feature or change:** Add **Duplicate as draft** with a confirmation/review page. Copy category, bilingual descriptive fields, threshold, and variant labels/price overrides; generate no sale, no stock, no featured state, and require new unique product/variant SKUs before publication. Copy images only through new storage keys or omit them by default—the current `ProductImage.storageKey` is unique and must not be shared unsafely.
- **Customer benefit:** More consistent product information and fewer catalog entry errors.
- **Admin benefit:** Faster creation of similar products without weakening validation.
- **Revenue or profitability mechanism:** Reduces admin labor and shortens catalog launch time; indirect revenue effect only.
- **Evidence from the current website:** `ProductForm.tsx` contains bilingual core fields, sales, multiple image metadata fields, and repeatable variants. `ProductStatus.DRAFT` already exists. `ProductRowActions.tsx` has no duplicate action.
- **Main routes/files/modules affected:** `/{locale}/admin/products`, `/{locale}/admin/products/[id]`, admin product API/mutations/schemas, image storage adapter, audit log.
- **Database changes:** None required.
- **External service or recurring cost:** Additional image storage only if image files are explicitly copied.
- **Security/privacy considerations:** Admin-only, same-origin mutation, audit `PRODUCT_DUPLICATED`, bounded image copy, and no user-controlled storage paths.
- **Arabic/English considerations:** Review both languages before publish; identify which fields were copied and which unique fields are required.
- **Phone/tablet considerations:** Keep the confirmation concise and reuse the existing responsive product form; do not introduce a wide comparison dialog.
- **Risks:** Duplicate SKUs, accidental publication, shared-file deletion, and copied outdated sale terms. Draft/zero-stock defaults and independent storage keys mitigate these.
- **How success should be measured:** Median product-entry time, number of duplicated drafts published, validation errors per create, and corrective edits within 24 hours.
- **Scope classification:** Fits current scope.
- **Scores:** Customer value 1; Admin value 5; Revenue potential 2; Operational value 3; Implementation effort 3; Maintenance cost 2; Technical risk 3; Business-decision dependency 1.

### REC-005 — Turn dashboard and report signals into actionable work queues

- **Category:** Admin productivity; reporting; inventory operations.
- **Priority:** High.
- **Time horizon:** Implement now.
- **Size:** Small to medium.
- **Current behavior:** The dashboard and report service already calculate new orders, stock alerts, restock priority, inactive customers, products in carts but not ordered, no-sale products, top category, wishlists, and frequent pairs. Most values are text/cards; the admin must navigate and recreate filters manually.
- **Observed limitation or opportunity:** JYS already pays the query/mental cost of generating useful signals but stops before the next operational action.
- **Proposed feature or change:** Make metric/insight cards link to exact filtered orders, products, inventory, or customers. Add a concise **Needs attention** panel ordered by safe rules: new orders, out of stock, low stock, expired sales, and draft products. Preserve current forms as the action surface rather than adding risky inline mutations. Add CSV/print for a filtered restock list using existing export safety.
- **Customer benefit:** Indirectly improves availability and order response speed.
- **Admin benefit:** Reduces navigation, repeated filter entry, and missed daily tasks.
- **Revenue or profitability mechanism:** Potentially reduces stockouts and order-processing delay; it does not prove demand or suggest contacting customers without consent.
- **Evidence from the current website:** `admin/page.tsx`, `admin/reports/page.tsx`, and `src/lib/reports/service.ts` already calculate the signals; `admin/inventory` already accepts search/state filters; dashboard stock rows and most insight rows lack exact drill-through.
- **Main routes/files/modules affected:** Admin dashboard, reports, orders, products, inventory, customers, report service/CSV query helpers.
- **Database changes:** None for links/queues/restock export.
- **External service or recurring cost:** None.
- **Security/privacy considerations:** Keep all pages admin-authorized. Do not turn inactive/unconverted customer data into unsolicited marketing; that belongs to REC-013.
- **Arabic/English considerations:** Localize action verbs, empty states, and query labels; preserve numeric/SKU direction inside RTL.
- **Phone/tablet considerations:** Use stacked action cards on phones and existing contained table scrolling for detailed queues.
- **Risks:** Too many alerts become noise. Show only actionable states, count them, and let the admin clear them by completing the underlying work.
- **How success should be measured:** Click-through from signals, time from new order to first status update, low-stock duration, expired-sale cleanup time, and admin task completion rate.
- **Scope classification:** Fits current scope.
- **Scores:** Customer value 2; Admin value 5; Revenue potential 3; Operational value 5; Implementation effort 2; Maintenance cost 2; Technical risk 2; Business-decision dependency 1.

## Tier 2 — Valuable after launch

### REC-006 — Send reliable transactional order-status notifications

- **Category:** Trust; customer communication; order operations.
- **Priority:** Medium.
- **Time horizon:** After launch, or before launch only if the production email provider and BUG-001 through BUG-003 are resolved.
- **Size:** Medium to large.
- **Current behavior:** JYS sends an order-received email through a replaceable console/Resend adapter. Customers otherwise revisit order history. Admin status changes record time and a currently internal note.
- **Observed limitation or opportunity:** Cash orders and third-party delivery benefit from clear confirmation, ready, dispatched, delivered/collected, and cancellation communication, but adding messages to the current fire-and-forget path would amplify its reliability defect.
- **Proposed feature or change:** After separating public and internal text, create a transactional outbox in the same database transaction as a meaningful status change. Deliver localized, idempotent email asynchronously with bounded retries and visible admin delivery state. Start with Confirmed, Ready for pickup, Sent to delivery company, Delivered/Collected, and Cancelled. Do not add promotional content.
- **Customer benefit:** Less uncertainty and fewer manual account checks.
- **Admin benefit:** Fewer “where is my order?” calls and an auditable send state.
- **Revenue or profitability mechanism:** Primarily trust and support-labor reduction; any cancellation reduction must be measured.
- **Evidence from the current website:** `src/lib/email`, `OrderStatusHistory`, admin order transitions, and order confirmation already exist; no notification/outbox model or status-message sender exists.
- **Main routes/files/modules affected:** Admin order update service/API, email adapter/templates, worker/cron entry point, admin order detail, settings and setup documentation.
- **Database changes:** Yes—recommended outbox/delivery-attempt records and optionally a public customer-facing status message distinct from the internal note.
- **External service or recurring cost:** Resend or another email provider, verified sending domain, and possibly a worker/cron host. Cost depends on volume/provider tier.
- **Security/privacy considerations:** Transactional purpose only, minimal order data, signed/account links, sanitized templates/logs, retry limits, and delivery metadata retention. Email is not a secure channel for sensitive address notes.
- **Arabic/English considerations:** Store the order/customer locale at send time or use profile preference; create genuine RTL templates, not mixed-direction string interpolation.
- **Phone/tablet considerations:** Email must be responsive and account links must return to the correct localized mobile page.
- **Risks:** Duplicate sends, out-of-order sends, provider outage, and ambiguous public copy. Idempotency keys and sequence-aware processing are required.
- **How success should be measured:** Delivery/failure/retry rates, duplicate-send rate, status-page visits from email, support-contact volume, and cancellation rate (with a pre-feature baseline).
- **Scope classification:** Extends current scope; requires operating-process change and privacy review.
- **Scores:** Customer value 5; Admin value 3; Revenue potential 2; Operational value 4; Implementation effort 4; Maintenance cost 3; Technical risk 3; Business-decision dependency 3.

### REC-007 — Add privacy-conscious funnel and search diagnostics

- **Category:** Reporting; marketing; conversion measurement.
- **Priority:** Medium.
- **Time horizon:** After launch, before making optimization claims.
- **Size:** Medium to large.
- **Current behavior:** Product views, active carts, wishlists, orders, and report aggregates exist. Search operates through URL query state, but search terms/no-result searches, checkout stages, promotion source, and add-to-cart events are not retained as a coherent funnel.
- **Observed limitation or opportunity:** The admin can see totals but cannot distinguish discovery failure, product-page friction, cart drop-off, account/login friction, or checkout validation drop-off. The current test-seeded database cannot supply a trustworthy baseline.
- **Proposed feature or change:** Define a small first-party event taxonomy: search submitted/no results, product viewed, add to cart, checkout started, validation failed by non-sensitive reason code, and order completed. Use anonymous session IDs before login and user ID only after authentication, with short retention and aggregation. Add product-view-to-cart, cart-to-order, wishlist-to-order, search-no-result, sale conversion, and fulfillment conversion reports.
- **Customer benefit:** Indirect—future improvements can target actual friction instead of assumptions.
- **Admin benefit:** Better catalog, promotion, and UX decisions.
- **Revenue or profitability mechanism:** Enables measurement and prioritization; it does not itself create revenue.
- **Evidence from the current website:** `ProductView`, `Cart`, `WishlistItem`, `Order`, and report product metrics exist; there is no search/event model or promotion attribution field.
- **Main routes/files/modules affected:** Catalog/search, product tracker, cart/checkout, reports service/page/CSV, privacy content, retention job.
- **Database changes:** Yes—prefer a minimal event/search aggregate model with indexed timestamps and scheduled retention, or a carefully selected analytics service.
- **External service or recurring cost:** None for a small first-party design beyond database/storage/maintenance; a hosted analytics platform would add recurring cost and consent/configuration work.
- **Security/privacy considerations:** No raw address, note, password, or full search URL in events; avoid durable IP/device fingerprinting; document retention and consent/legal basis; restrict granular data to admins.
- **Arabic/English considerations:** Record locale separately, normalize query whitespace without merging Arabic/English meanings, and report both locale-specific and combined funnels.
- **Phone/tablet considerations:** Segment by broad viewport class, not fingerprintable device model; track errors without adding client weight that harms slow connections.
- **Risks:** Bad taxonomy produces misleading dashboards; test fixtures can pollute results. Mark test records/environments and validate event deduplication.
- **How success should be measured:** Event completeness, duplicate rate, unknown-step rate, percentage of searches with no results, funnel conversion by locale/device class, and decisions documented from the data.
- **Scope classification:** Fits current scope; requires privacy review.
- **Scores:** Customer value 2; Admin value 4; Revenue potential 4; Operational value 3; Implementation effort 4; Maintenance cost 3; Technical risk 3; Business-decision dependency 2.

### REC-008 — Upgrade related products to evidence-based complements

- **Category:** Average order value; merchandising.
- **Priority:** Medium.
- **Time horizon:** After enough genuine multi-item fulfilled orders exist.
- **Size:** Medium.
- **Current behavior:** Product pages show related products selected from the same category. The report service computes a “Frequently purchased together” pair only when at least two delivered/collected orders contain the pair.
- **Observed limitation or opportunity:** Same-category products can be substitutes rather than complements. The report already has a better data signal, but the current local records average one line item per order and are test-contaminated, so there is no defensible live recommendation yet.
- **Proposed feature or change:** When a minimum clean-data threshold is reached (for example, 50 genuine fulfilled multi-item orders and at least 3 pair occurrences), rank in-stock complementary pairs and show **Often bought with** on product/cart pages. Fall back to current same-category related items. Allow a small admin override for deliberately curated complements; never auto-add an item or imply a discount.
- **Customer benefit:** Faster discovery of useful combinations such as a tool and its consumable/accessory.
- **Admin benefit:** Reuses actual selling patterns and supports controlled merchandising.
- **Revenue or profitability mechanism:** Potentially raises average order value and units per order; requires controlled measurement.
- **Evidence from the current website:** Same-category `related` is rendered in the product route; delivered-order pair aggregation already exists in `src/lib/reports/service.ts`; no customer-facing pair use or curated relationship exists.
- **Main routes/files/modules affected:** Product route, cart, catalog repository, reports service, optional admin product merchandising controls.
- **Database changes:** None for aggregate-only v1; a curated `ProductRelationship` model would require a migration.
- **External service or recurring cost:** None initially.
- **Security/privacy considerations:** Use aggregate counts only and enforce a minimum cohort threshold; never expose individual purchase histories.
- **Arabic/English considerations:** Use concise truthful labels; curated product text already has bilingual content.
- **Phone/tablet considerations:** One contained horizontal list or a two-column grid; keep the main cart action dominant and avoid layout overflow.
- **Risks:** Sparse data, substitute recommendations, stale availability, and popularity bias. Thresholds, stock checks, fallback, and admin override mitigate them.
- **How success should be measured:** Recommendation impression-to-click, add rate, attach rate, units/order, AOV, and removal rate compared with the existing related-products baseline.
- **Scope classification:** Fits current scope.
- **Scores:** Customer value 4; Admin value 2; Revenue potential 5; Operational value 2; Implementation effort 3; Maintenance cost 3; Technical risk 3; Business-decision dependency 2.

### REC-009 — Capture structured cancellation reasons and order-stage duration

- **Category:** Reporting; order operations.
- **Priority:** Medium.
- **Time horizon:** After launch, once genuine orders can establish a baseline.
- **Size:** Medium.
- **Current behavior:** Cancellation uses the same optional free-text internal note as other status transitions. `OrderStatusHistory.createdAt` can reconstruct stage timing, but reports expose counts, not reasons or time in each state.
- **Observed limitation or opportunity:** The admin cannot reliably distinguish customer cancellation, duplicate order, unreachable customer, stock issue, delivery issue, or admin/test cancellation. Free text is hard to aggregate and is currently implicated in BUG-001.
- **Proposed feature or change:** Require a localized structured reason when cancelling, retain an optional **private internal detail**, and calculate median/percentile time between status transitions by fulfillment method. Keep customer-visible cancellation wording separate and neutral. Mark test/seed orders so operational reports can exclude them.
- **Customer benefit:** More accurate and less confusing status communication.
- **Admin benefit:** Identifies process bottlenecks and recurring cancellation causes.
- **Revenue or profitability mechanism:** Can guide changes that reduce avoidable cancellations and fulfillment delay; it does not reduce them by itself.
- **Evidence from the current website:** `OrderStatusHistory` has only `note`; admin transition UI labels it internal; reports count cancellation and status but do not group reasons or durations.
- **Main routes/files/modules affected:** Prisma order history, order validation/service, admin order actions/detail, customer order serialization, reports/CSV, seed/E2E marking policy.
- **Database changes:** Yes—reason code and private/public message separation; optional environment/source marker for test data.
- **External service or recurring cost:** None.

## Tier 3 — Scaling and operational maturity

### REC-010 — Add purchase cost, supplier, margin, and stock-turnover data

- **Category:** Profitability; inventory; purchasing.
- **Priority:** Medium when the admin is ready to maintain cost data.
- **Time horizon:** Before scaling purchasing or making margin-based decisions.
- **Size:** Large.
- **Current behavior:** Reports calculate revenue from product-only order totals and units. Products/variants have selling prices and stock, but no purchase cost, supplier, supplier SKU, lead time, minimum order quantity, or cost history.
- **Observed limitation or opportunity:** Revenue can rank products but cannot show gross margin, inventory value, days of cover, or profitable restock priority. Adding a chart without trustworthy cost inputs would be misleading.
- **Proposed feature or change:** First define the bookkeeping policy: landed-cost components, tax/currency handling, variant-level cost, effective dates, supplier ownership, and who updates them. Then add cost history and supplier records, snapshot unit cost to order/inventory movements, and report gross-margin estimate, inventory valuation, stock turnover, dead stock, and reorder candidates. Keep suggestions advisory.
- **Customer benefit:** Indirect—better availability and product selection.
- **Admin benefit:** Purchasing and pricing decisions based on profit rather than revenue alone.
- **Revenue or profitability mechanism:** Potentially improves margin, reduces dead inventory, and reduces stockouts; accuracy depends entirely on maintained cost/lead-time data.
- **Evidence from the current website:** `Product`, `ProductVariant`, `OrderItem`, and `InventoryAdjustment` contain no cost/supplier fields; current reports expose revenue and units only.
- **Main routes/files/modules affected:** Prisma/migrations, product/variant admin, inventory, reports/CSV, order/inventory snapshots, audit log.
- **Database changes:** Significant—Supplier, cost history/current cost, optional supplier product, lead time/MOQ, and cost snapshots.
- **External service or recurring cost:** None initially; accounting integration would be a separate decision and cost.
- **Security/privacy considerations:** Cost and margin are commercially sensitive; admin authorization and audit coverage are mandatory. Future staff roles should restrict access.
- **Arabic/English considerations:** Supplier names may be one language; business labels/reasoning must be bilingual and currency direction safe.
- **Phone/tablet considerations:** Summary cards on mobile; detailed valuation tables contained or desktop-oriented without widening the page.
- **Risks:** False precision, old costs, currency variation, and double-counted landed cost. A written operating policy is a prerequisite.
- **How success should be measured:** Cost-data completeness/freshness, inventory value reconciliation, gross-margin variance, dead-stock value, stockout days, and purchase suggestion acceptance.
- **Scope classification:** Extends current scope; requires operating-process change and a business decision.
- **Scores:** Customer value 1; Admin value 5; Revenue potential 5; Operational value 5; Implementation effort 5; Maintenance cost 4; Technical risk 4; Business-decision dependency 5.

### REC-011 — Add validated bulk catalog and inventory workflows at a volume threshold

- **Category:** Admin productivity; inventory operations.
- **Priority:** Future consideration.
- **Time horizon:** Only when the catalog exceeds roughly 100 active SKUs or the admin changes more than about 20 rows weekly.
- **Size:** Large.
- **Current behavior:** CSV is export-only for reports. Product creation and stock correction are deliberately one item at a time with full validation and audit reasons.
- **Observed limitation or opportunity:** Individual controls are safer at the current six-active-product scale. They will become repetitive at a substantially larger catalog or supplier delivery batch.
- **Proposed feature or change:** Add downloadable bilingual templates and a preview/dry-run import that validates every row before an all-or-nothing transaction. Separate catalog metadata, sale changes, and stock adjustments; require a batch reason and generate per-row audit/ledger records. Add optional EAN/UPC/barcode fields only when JYS actually scans them.
- **Customer benefit:** Indirect—faster catalog/stock updates and fewer stale availability states.
- **Admin benefit:** Reduces repetitive entry at scale.
- **Revenue or profitability mechanism:** Saves labor and can reduce stock-update delay; low current-volume benefit.
- **Evidence from the current website:** Five safe CSV exports exist, but no import route/parser; product and inventory forms perform single-item mutations; SKU is already unique but there is no barcode field.
- **Main routes/files/modules affected:** Admin products/inventory, new import preview route/service, validation, transactions, audit/ledger, CSV utilities, setup documentation.
- **Database changes:** None for SKU-based bulk updates; optional barcode/supplier SKU fields require a migration.
- **External service or recurring cost:** None.
- **Security/privacy considerations:** Admin-only, strict size/row limits, formula-safe exports, no executable spreadsheet content, dry run, transaction, idempotency, and retained batch audit.
- **Arabic/English considerations:** UTF-8 BOM/template headers, bilingual validation messages, and explicit locale-independent field keys.
- **Phone/tablet considerations:** File import is primarily desktop/tablet; status and rollback results must remain readable on phones.
- **Risks:** A malformed batch can damage many records. Do not implement until the volume justifies the operational risk.
- **How success should be measured:** Rows per batch, validation-failure rate, rollback rate, time saved, stock reconciliation errors, and manual corrections after import.
- **Scope classification:** Fits current scope when the stated need exists; requires operating-process change.

### REC-012 — Expose audit history and split admin permissions when staff grows

- **Category:** Governance; admin operations; security.
- **Priority:** Future consideration.
- **Time horizon:** Before a second operational staff role receives admin access.
- **Size:** Medium to large.
- **Current behavior:** `AuditLog` captures administrative mutations, but there is no audit-history page. `UserRole` has only CUSTOMER and ADMIN, so every administrator has broad authority.
- **Observed limitation or opportunity:** One owner/admin can use the current model. Multiple staff handling orders, stock, content, and reports need traceability and least privilege.
- **Proposed feature or change:** First add a read-only, filterable audit viewer with entity links and redacted metadata. When a second staff role is real, define capabilities such as Owner, Orders, Catalog/Inventory, and Content/Reports, enforcing them in server authorization before hiding UI links.
- **Customer benefit:** Indirect protection from unauthorized or mistaken changes.
- **Admin benefit:** Faster investigation, accountability, and safer delegation.
- **Revenue or profitability mechanism:** Primarily risk/labor reduction, not direct revenue.
- **Evidence from the current website:** `AuditLog` exists and admin mutations write to it; no admin audit route appears in `AdminShell`; authorization accepts a single ADMIN role.
- **Main routes/files/modules affected:** Prisma roles/permissions, auth session/authorization, AdminShell, audit repository/page/export, all admin API capability checks.
- **Database changes:** None for audit viewing; yes for durable role/capability assignments.
- **External service or recurring cost:** None.
- **Security/privacy considerations:** Audit data can contain sensitive metadata; redact secrets/addresses, restrict exports, make logs append-only, and test every server endpoint—not just navigation.
- **Arabic/English considerations:** Localize known actions/entities while preserving technical IDs LTR and searchable.
- **Phone/tablet considerations:** Use filters plus event cards or contained tables; details must not overflow.
- **Risks:** Partial permission enforcement is worse than a single honest admin role. Do not release roles until endpoint coverage is complete.
- **How success should be measured:** Percentage of admin endpoints mapped to capabilities, unauthorized-access tests, audit lookup time, and high-risk actions attributable to an actor.
- **Scope classification:** Fits current scope at multi-staff scale; requires operating-process change.
- **Scores:** Customer value 1; Admin value 4; Revenue potential 1; Operational value 5; Implementation effort 4; Maintenance cost 3; Technical risk 4; Business-decision dependency 3.

### REC-013 — Add distributed operational resilience only before multi-instance scale

- **Category:** Technical and operational resilience.
- **Priority:** Future consideration, with existing manual launch gates completed first.
- **Time horizon:** Before multiple application instances, high email volume, or storage beyond one durable mounted instance.
- **Size:** Large.
- **Current behavior:** Rate limiting is process memory; sessions are signed cookies with database user revalidation; local uploads require a durable mounted path; email is direct and non-durable; logging is application console based. These choices are proportionate to one small instance.
- **Observed limitation or opportunity:** Multiple instances would not share rate-limit state or local files, and durable notification delivery/operational alerting would be weak. Adding enterprise infrastructure now would be premature.
- **Proposed feature or change:** At a defined scaling trigger, move uploads behind the existing storage interface to object storage, use a shared rate limiter, introduce the notification outbox/worker from REC-006, add privacy-aware error/latency monitoring, and document restore drills. Preserve simple signed sessions unless actual revocation/concurrency needs justify a shared session store.
- **Customer benefit:** Better availability and predictable recovery.
- **Admin benefit:** Faster incident detection and fewer manual recovery steps.
- **Revenue or profitability mechanism:** Reduces outage/data-loss risk rather than increasing normal conversion.
- **Evidence from the current website:** `src/lib/storage` currently implements local storage only; `src/lib/security/rate-limit.ts` stores a process Map; email has no queue; setup documentation already flags backups, durable uploads, and production email.
- **Main routes/files/modules affected:** Storage/email/security adapters, worker/hosting config, health/observability, backup/runbook documentation.
- **Database changes:** Notification outbox and possibly job tables; none necessarily for object storage/rate limiting.
- **External service or recurring cost:** Object storage, shared cache/rate-limit service, monitoring, worker/cron, and email provider.
- **Security/privacy considerations:** Vendor data regions, access-key rotation, signed/private asset policy, log scrubbing, least privilege, retention, and restore testing.
- **Arabic/English considerations:** Operational alerts may be English internally; customer-facing errors and queued messages remain bilingual.
- **Phone/tablet considerations:** No direct layout impact; preserve fast mobile loading and avoid heavy client monitoring SDKs.
- **Risks:** Vendor lock-in, recurring cost, needless complexity, and migration mistakes. Trigger the work from real deployment topology/volume, not fashion.
- **How success should be measured:** Restore-time and restore-point objectives, upload availability, queue delay/failure rate, rate-limit consistency, incident detection time, and service cost per order.
- **Scope classification:** Fits current scope at scale; requires operating-process change and budget decisions.
- **Scores:** Customer value 2; Admin value 3; Revenue potential 2; Operational value 5; Implementation effort 5; Maintenance cost 4; Technical risk 4; Business-decision dependency 4.

## Tier 4 — Strategic business decisions

### REC-014 — Consider consent-based retention messages only after policy and channel decisions

- **Category:** Customer retention; marketing.
- **Priority:** Future consideration.
- **Time horizon:** Only when JYS has clean post-launch data, an approved consent policy, a sending provider, and staff capacity to operate the program.
- **Size:** Large.
- **Current behavior:** Customers can wishlist items and the report identifies inactive customers/unconverted carts, but there are no per-purpose subscriptions, back-in-stock requests, price-drop subscriptions, reminder schedules, send history, suppression list, or unsubscribe center. `marketingOptIn` is one broad profile boolean.
- **Observed limitation or opportunity:** Back-in-stock or wishlist reminders could be useful, but using account/cart data for marketing without explicit purpose, frequency, and opt-out rules creates trust, privacy, and cost risk. WhatsApp/SMS adds provider and consent complexity.
- **Proposed feature or change:** If approved, start with opt-in email back-in-stock alerts for explicitly selected products. Add per-purpose consent, one-click unsubscribe, suppression, frequency caps, expiry, idempotent outbox delivery, and admin aggregate reporting. Consider price-drop or cart reminders only after the first program proves useful. Do not start with WhatsApp/SMS.
- **Customer benefit:** Timely availability information chosen by the customer.
- **Admin benefit:** Automated retention without manual customer-list handling.
- **Revenue or profitability mechanism:** Potential repeat conversion; depends on opt-in adoption, inventory events, deliverability, and provider cost.
- **Evidence from the current website:** `WishlistItem`, stock, sale pricing, `CustomerProfile.marketingOptIn`, and report signals exist; all purpose-specific consent/delivery models are absent.
- **Main routes/files/modules affected:** Wishlist/product UI, profile preferences, inventory/sale events, email/outbox, admin campaign aggregates, privacy policy.
- **Database changes:** Yes—purpose-specific subscriptions/consent evidence, notification state, suppression/unsubscribe, and delivery attempts.
- **External service or recurring cost:** Email provider initially; WhatsApp Business or SMS would add approval, templates, per-message fees, and operational support.
- **Security/privacy considerations:** Requires privacy review and possibly legal review. Consent must be specific, recorded, revocable, and separated from transactional messages; minimize retention and never expose recipient lists in CSV by default.
- **Arabic/English considerations:** Store preferred language per subscription/send and provide equivalent consent/unsubscribe text in both languages.
- **Phone/tablet considerations:** Subscription controls must be simple, non-coercive, and keyboard/screen-reader accessible; no prechecked opt-ins.
- **Risks:** Spam perception, poor deliverability, provider cost, duplicate messages, and unclear consent. A narrow opt-in pilot is the safe boundary.
- **How success should be measured:** Confirmed opt-in rate, delivery/bounce/complaint/unsubscribe rates, conversion within a defined window, incremental margin net of provider cost, and frequency-cap violations.
- **Scope classification:** Extends current scope; requires privacy review, possible legal review, operating-process change, and a business decision.
- **Scores:** Customer value 4; Admin value 2; Revenue potential 4; Operational value 2; Implementation effort 5; Maintenance cost 5; Technical risk 4; Business-decision dependency 5.
